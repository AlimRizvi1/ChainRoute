# ChainRoute Team Decisions

Phase 1 decisions and interface contracts approved by all three team members on 2026-10-15.

| # | Decision | Approved choice | Reason | Approval |
|---|---|---|---|---|
| 1 | Money unit and currency | INR, represented everywhere off-chain and on-chain as integer paise. The reference freight value `2500000` therefore means INR 25,000. | Integer minor units avoid floating-point errors in deductions and settlement. | Alim, Parth, and Elish approved, 2026-10-15 |
| 2 | Source of SLA deadline | For the single agreement created from an accepted plan, use the earliest stated deadline among the orders included in that plan. The backend derives it; clients cannot override it. The plan ETA is a prediction, not a contractual deadline. | Preserves the one-contract-per-plan API and ensures the aggregated agreement does not promise a later time than any included order. | Alim, Parth, and Elish approved, 2026-10-15 |
| 3 | Allocation and learning approach | OR-Tools CP-SAT for constrained allocation. Logistic regression predicts per-order on-time delivery probability from order/route features; use a clearly labelled heuristic fallback when the model is unavailable or untrained. | CP-SAT directly models capacity and compatibility constraints; the probability target feeds the on-time score and dashboard metric. | Alim, Parth, and Elish approved, 2026-10-15 |
| 4 | Unassigned orders and malformed AI input | Initial reason codes: `NO_COMPATIBLE_WAGON`, `NO_ROUTE`, `INSUFFICIENT_CAPACITY`, `NO_FEASIBLE_ASSIGNMENT`, `TIME_BUDGET_EXCEEDED`; Phase 6 adds `INCOMPATIBLE_WAGON_TYPE`. Invalid optimize requests return HTTP 400 using the shared error body and field-level `fields` map. | Stable machine-readable reasons let the platform explain dropped orders without coupling to Track 1 internals. | Alim, Parth, and Elish approved, 2026-10-15; Phase 6 extension approved by Alim, 2026-10-16 |
| 5 | HTTP errors | Use `{"error":{"code":"STRING_CODE","message":"human text","fields":{"field":"why"}}}` (`fields` optional); statuses per `docs/Plan.md` §8: 400, 401, 403, 404, 409, and 503. Also use 502 for invalid upstream responses and 504 for upstream timeouts as required by later phases. | Consistent error parsing across dashboard, platform, and service boundaries; 404 avoids disclosing unauthorized resources. | Alim, Parth, and Elish approved, 2026-10-15 |
| 6 | On-chain caller permissions | Operator creates agreements, releases payment, and closes contracts; assigned carrier confirms booking, posts shipment status, and confirms delivery; either contract party may raise a dispute; configured arbitrator/admin resolves it; reads are public. Carrier/party identity arguments must match `msg.sender`. | Matches the plan's operator/carrier model while enforcing party identity in the contract, not only in the backend. | Alim, Parth, and Elish approved, 2026-10-15 |
| 7 | Track 3 backend language | TypeScript on Node.js 22. No contract shape depends on this choice. | One language/toolchain for the API and dashboard owner, while keeping the wire contracts language-neutral. | Alim, Parth, and Elish approved, 2026-10-15 |
| 8 | Additional performance target | Backend read endpoints: p95 below 500 ms with 20 concurrent clients in normal demo conditions. No additional target is set for other endpoints; the optimizer retains the plan's qualitative target. | A measurable read-path target is useful for acceptance without over-constraining optimizer or blockchain latency. | Alim, Parth, and Elish approved, 2026-10-15 |
| 9 | Phase 3 synthetic categories, compatibility, and base | Cargo `grain`, `coal`, `steel`; wagon types `covered`, `open`, `flat`; strict pairs grain→covered, coal→open, steel→flat. Use `Yard-0` as the base and `Port-A`, `Plant-B`, `Depot-C`, and `Port-D` as destinations. | Reuses the Phase 1 fixture vocabulary, gives Phase 4/6 a deterministic compatibility table, and keeps generated routes consistent with the shared example. This is the synthetic-data domain, not a closed set for the open-string API schema. | Alim approved, 2026-10-16 |
| 10 | Phase 4 baseline order, departure, and route selection | Process by ascending priority number (1 first), then earliest deadline, then order ID. Use zero dwell time and the fixed synthetic start `2026-01-07T20:00:00Z`. Among feasible routes, choose shortest distance, then route ID; choose wagons by descending capacity, then wagon ID. Reject an assignment whose ETA misses the deadline as `NO_FEASIBLE_ASSIGNMENT`. | Gives scarce-capacity outcomes a stable priority order and makes sample plans reproducible. The approved Phase 1 unassigned-reason enum has no `INSUFFICIENT_WAGONS`, so capacity exhaustion uses `INSUFFICIENT_CAPACITY`. | Alim approved, 2026-10-16 |
| 11 | Phase 5 candidate scoring, cost, and alternatives | Charge 250 paise per wagon-kilometre; normalize any finite nonnegative weights, treating all-zero weights as equal thirds. Scale on-time as a probability, utilization as percent/100, and cost as `clamp(1 - cost/maxPossibleCost, 0, 1)`. Score = assigned-order coverage + normalized weighted metric mean / (order count + 1), so coverage takes precedence. Generate four deterministic greedy candidates and return at most three distinct alternatives. On-time probability uses `0.5 + 0.5 × deadlineSlack / (deadlineSlack + transitTime)` until Phase 7 supplies a trained prediction. | Implements transparent first-pass economics and prevents a cheap partial plan from beating a higher-coverage plan; varied deterministic heuristics supply alternatives without claiming global optimality. | Alim approved, 2026-10-17 |
| 12 | Phase 6 constraint search and budget | Use deterministic OR-Tools CP-SAT with one worker and seed 0. Use Phase 4's greedy assignment as both a warm-start hint and always-available incumbent. Default solver budget is 1 second; request override range is 0.05–10 seconds. Optimize assigned-order counts lexicographically by priority before applying weighted metric guidance. | Keeps a valid result available if search times out, bounds service resource use, and makes priority levels a hard ordering rule while preserving Phase 5 ranking among same-tier candidates. | Alim approved, 2026-10-16 |
| 13 | Phase 7 prediction target, training and lifecycle | Predict each assigned order's probability of delivery before its deadline using logistic regression on normalized deadline slack and cargo-specific transit variability. Train on 30,000 deterministic synthetic lognormal transit simulations; use an 80/20 stratified holdout split with seed 42. Accept held-out probability MAE ≤ 0.10 against the simulator's known probability. Retrain explicitly when simulation assumptions or training data change, and identify each fitted artifact by a hash of its training data and parameters. Use the existing heuristic when the artifact is missing or the assigned cargo type is unsupported; report `mixed` when a plan combines model and fallback predictions. | Provides a reproducible learned estimate without making a fresh install depend on historical run data; the response reports the model/fallback method and stable model version for Phase 8 traceability. | Alim approved, 2026-10-16 |
| 14 | Phase 8 run-log storage | Store one immutable JSON snapshot per run in a Track-1-owned SQLite database with unique run IDs; use WAL for concurrent access, `AI_RUN_LOG_PATH` for local configuration, and a dedicated Compose named volume for persistence. Expose `GET /v1/runs/{runId}`. | Keeps the AI engine independently deployable without coupling to Track 3's PostgreSQL or introducing a remote logging dependency; retains diagnostic input and failure details across Compose restarts. | Selected for Phase 8 implementation, 2026-10-16 |
| 15 | Phase 10 agreement validation and operator | The deployer is the immutable operator; require non-empty plan ID, non-zero shipper/carrier addresses, positive freight value, future SLA deadline, positive penalty block length, at least one wagon, and non-zero terms hash. Shipper and carrier may be the same address. Store history on-chain and emit matching lifecycle events. | Prevents incomplete or unbookable agreements while keeping party identity semantics aligned with the frozen interface; a single deployment identity provides the configured operator for the prototype. | Selected for Phase 10 implementation, 2026-10-17 |
| 16 | Phase 11 shipment status and timestamp policy | Use frozen statuses `Dispatched`, `CheckpointReached`, and `ArrivedAtDestination`; only the assigned carrier posts while `Booked`/`InTransit`. Require nondecreasing timestamps from booking onward; equal timestamps are accepted. The first status transitions to `InTransit`; subsequent statuses leave it there. | Preserves chronological on-chain history while allowing two milestones to share a timestamp when the source clock has only second-level precision. | Selected for Phase 11 implementation, 2026-10-17 |
| 17 | Phase 12 SLA, penalty, demurrage, and delivery timestamp | Use the first `ArrivedAtDestination` timestamp; without one, demurrage is zero. Round any partial late block or billable holding hour up. Cap penalty at freight, then cap demurrage at the remaining freight. The assigned carrier supplies delivery time, which must not regress the latest status or exceed current chain time. | Makes the deductions reproducible from the on-chain event history, handles partial intervals conservatively, and guarantees settlement deductions cannot exceed gross freight. | Selected for Phase 12 implementation, 2026-10-17 |
| 18 | Phase 13 payment release and closure | Keep release as a separate operator-only, accounting-only action after `PenaltyCalculated`; store net payment and emit its event without transferring assets. Allow operator-only close after release; reject retries and every state change after closure. | Separates settlement recording from delivery evaluation so a release can be retried safely at the API boundary while the contract itself prevents duplicate payouts. | Selected for Phase 13 implementation, 2026-10-17 |
| 19 | Phase 14 dispute permissions and lifecycle | The deploying operator is the arbitrator; either party may raise only before release while in `PenaltyCalculated`, with `raisedBy == msg.sender`. Permit another dispute after resolution before release; apply outcomes to deductions in effect at each raise. Permit arbitrator/party overlap. | Keeps the prototype role model simple and permits a second review without rewriting any earlier event or history; each decision is auditable as a new entry. | Selected for Phase 14 implementation, 2026-10-17 |
| 20 | Phase 15 persistence, migrations, and demo seed | **Proposed by Elish; pending team review.** Use ordered PostgreSQL SQL migrations with checksums and a transaction-scoped advisory lock; retain linked Track 1 run metadata/input snapshot in the platform alongside the optimizer's authoritative SQLite diagnostic trace; seed wagon/route master data from `samples/plentiful-dataset.json`; do not seed old sample orders. Seed four stable local role users and never overwrite existing users or master data. | Reuses the current `pg` dependency and checked fixture without adding migration dependencies or a runtime connection from Track 3 to Track 1. Linked snapshots preserve platform-level run/plan/order traceability. Avoiding old orders prevents stale deadlines from appearing in the demo. Stable role mappings prepare later UI/API work while private keys remain outside PostgreSQL. This decision adds storage responsibilities, so all three tracks must review before later tracks rely on them. | Elish implementation proposal, 2026-10-18; team review pending |

| 21 | Phase 16 credentials, tokens, role checks, and audit | Store passwords as independently salted Node `scrypt` hashes (`N=131072`, `r=8`, `p=1`, 16-byte salt, 64-byte key); compare derived keys with a timing-safe comparison and cap password input at 256 UTF-8 bytes. Issue HS256 JWT bearer access tokens for 15 minutes with a fixed issuer and audience, verify only HS256, recheck the active database user and exact role on every request, and omit refresh tokens for the prototype. Require an environment-provided token secret of at least 32 bytes in production; local development may use the ignored root `.env` or a per-process random secret. Map authenticated identities to `users.chain_address`; signer key custody remains a Phase 18 decision. Central permissions default to deny, scope shipper/carrier resources to their own/assigned records, rate limit login to five requests per minute per IP, and record each mutating request once under a unique request ID without request bodies or credentials. | Uses Node crypto for password derivation and vetted Fastify plugins for JWT verification and rate limiting; avoids storing raw passwords or signing keys in PostgreSQL; a short access-token life and per-request active-user check promptly revoke disabled accounts. No refresh mechanism keeps the prototype's token lifecycle explicit. | Selected for Phase 16 implementation, 2026-10-18 |

| 22 | Phase 18 contract relay identities, money, and retry safety | Local Compose signs through the deterministic Hardhat accounts already mapped to the seeded Administrator/operator, Shipper, and Carrier addresses; this uses unlocked RPC accounts only on the isolated local development chain. Production signs with operator, shipper, and carrier private keys supplied as runtime secrets and verifies each key's address against the active `users.chain_address` mapping. Freight and deductions remain integer paise with no rounding at the API boundary. `slaDeadline` is derived as the earliest deadline among assigned orders; `wagonCount` is derived from the accepted assignment snapshot. Hash the canonical, recursively key-sorted JSON document containing `planId`, shipper address, carrier address, and normalized terms (including ISO UTC deadline) with keccak256 before submitting the agreement. Use an idempotency key bound to a request hash and persist confirmed transaction results; on a retry with an uncertain result, reconcile from contract state/events before considering another transaction. Payment release and contract closure are separate Administrator/operator actions so the parties retain the agreed pre-release dispute window. | Reuses the local Track 2 account model for team integration while making the public development keys unusable in production; binds the agreement to the complete commercial terms and keeps contract money exact. Persistent operation rows plus on-chain reconciliation protect retries across backend restarts. | Elish implementation proposal, 2026-10-18; team review pending |

| 23 | Phase 19 event synchronization, live updates, and outage handling | Poll the configured settlement contract every 2 seconds using a PostgreSQL advisory lock and persisted chain/block cursor; reconcile cached contract and payment state from the on-chain ledger every 30 seconds. Cache lifecycle and delivery events idempotently. Push authenticated WebSocket events only to the contract's shipper and carrier; administrator/auditor overviews omit commercial terms and payment values. Reads use the PostgreSQL cache during RPC outages. Return HTTP 202 for state changes queued during outages; retry with exponential backoff capped at 30 seconds while preserving the original request and idempotency key. | Gives horizontally deployed API instances a single sync owner, durable event progress, party-only notifications, and retryable writes without making the database the settlement authority. | Elish implementation proposal, 2026-10-18; team review pending |
| 24 | Phase 20 dashboard foundation, session, and motion | Use React Router for role-guarded routes; keep the short-lived access token in tab-scoped session storage and clear it on expiry or an API 401. Mirror the backend's four-role permission matrix in dashboard navigation and route guards. Support mock and real API modes, label synthetic data, and use GSAP route transitions only when the user has not requested reduced motion. Keep all four roles equally prominent in the shared dashboard shell. | Declarative routes and centralized session/API handling provide consistent access and failure states. Tab-scoped storage limits token persistence, while the mock switch supports local UI work without backend credentials. Reduced-motion handling preserves accessibility and role balance avoids privileging one workflow before role-specific screens are built. | Elish implementation proposal, 2026-10-18; team review pending |
| 25 | Phase 21 overview data and visual direction | Use Yard Marks across the dashboard: evergreen ink, stone ground, chalk surfaces, signal brass, rust, condensed display type, and compact square panels. Define “today” using UTC. Draw a custom SVG lifecycle schematic without external map tiles because the API exposes contract states but no trustworthy geographic coordinates; keep a text shipment list alongside it. Cap alert rows at five and refresh overview data every 15 seconds. `/dashboard/summary` is available only to Shipper and Administrator; Carrier and Auditor use their all-role redacted contract list. Administrator summary values stay aggregate and omit financial totals. | The selected design gives the freight workflow a distinct visual identity. UTC keeps API counts reproducible; a schematic marks only confirmed in-transit state without implying invented positions. Bounded alerts and the text list support performance, keyboard access, and a tile-free fallback. The role boundary preserves the existing authorization matrix and financial redaction. | Yard Marks chosen by the user; implementation proposal by Elish, 2026-10-18; team review pending |
| 26 | Phase 22 optimization workshop | Make the three weight dials normalize to visible shares and send those normalized values to `/optimizations/run`. Keep each what-if result as a separately saved plan; compare estimated cost and on-time probability against the preceding plan. Show returned order assignments, wagon IDs, route, ETA, on-time probability, readable unassigned reasons, and ranked alternatives. Submit order intake independently of optimizer availability. Contract acceptance requires a registered carrier wallet and explicit terms; wagon count is derived from the selected plan. Reuse a plan-scoped idempotency key and keep HTTP 202 queued operations on screen so the user can safely check again. | The allocation screen follows the actual API contract while making optimizer choices and trade-offs legible. Independent order intake preserves work during a Track 1 outage. Derived wagon count prevents disagreement with immutable plan assignments, and idempotent retry safely reconciles delayed chain writes. | Elish implementation proposal, 2026-10-18; team review pending |
| 27 | Phase 23 contract ledger, privacy, and lifecycle actions | Search contract IDs, plan IDs, parties, and states in the role-scoped list; load further backend pages by cursor. Display all eight lifecycle states and the dispute branch. Show terms, assignments, financial values, and chronological event metadata only to Shipper/Carrier parties; Administrator/Auditor receive lifecycle fields and public event metadata without commercial or payment details. Gate booking, shipment, delivery, dispute, resolution, release, and close actions by the same role/state matrix as the backend; use idempotency keys and preserve queued action payloads for safe retry. Keep `404` ownership failures indistinguishable as not found/out of scope. | The interface stays aligned with the API's party privacy and permission boundary while giving auditors enough public event metadata to follow state changes. Cursor paging avoids silently truncating the ledger, and state-aware actions reduce avoidable conflicts while the backend remains authoritative. | Elish implementation proposal, 2026-10-18; team review pending |
| 28 | Phase 24 tracking, settlement display, and event privacy | Compare the immutable plan ETA (until delivery) or recorded delivery timestamp to the contract SLA; do not imply live GPS/location. Show the exact integer-paise amounts returned by the contract API, while explaining penalty blocks and billable holding hours from cached chain event details and the contract terms. Keep calculation-event payloads party-only; Administrator/Auditor may see public shipment and delivery milestone metadata. Label disputed, pending, and recorded settlement states in text as well as color. | Separates prediction from observed events, preserves the chain/API as the settlement authority, and gives parties an auditable explanation without exposing calculation details to nonparties. | Selected for Phase 24 implementation, 2026-10-18 |
| 29 | Phase 25 dashboard alerts and exports | In real API mode, authenticate the dashboard WebSocket with the current tab token, receive only server-filtered party events, verify the returned contract party IDs again before notifying or refreshing views, reconnect with bounded exponential backoff, and end the session when the token expires. In mock mode, label the 15-second overview refresh as sample activity. Export the currently displayed allocation rows and settlement record to CSV; quote every cell, neutralize spreadsheet formulas, preserve integer paise, and disable export until all required data is loaded. | Reuses Phase 19's push boundary while adding defense in depth in the UI; read-only auditors and nonparty administrators continue to use the existing polling and redaction rules. Local CSV keeps the download consistent with the rendered result and never recomputes settlement money. | Selected for Phase 25 implementation, 2026-10-18 |
